# Negative proof (wasix-php 8.5.13-1)

**Date:** 2026-11-28

## 8.5.13-1: PHP 8.5.13 (#2246)

Renovate's bump to PHP 8.5.13 failed host-build (ladder-build run
46102707302): `Hunk #1 FAILED at 81000`, then `homescoop wasix-php:
0001-configure-wasi-host.patch does not apply to php 8.5.13 (a patch
failure, not a checksum error)`. PHP 8.5.13's `configure.ac` only changes
the version, but its shipped `configure` was generated by Autoconf 2.72
instead of 2.71. 2.72 writes the else branch of `AC_CHECK_HEADER([ucontext.h])`
as `else case e in #( e) … ;; esac` where 2.71 had `else $as_nop`, and it
quotes `'$ac_pwd'` where 2.71 had a backquote. The fibers hunk now nests its
`case $host_os` inside that branch. Autoconf's own output for the patched
`configure.ac` (2.73, run on a scratch copy) nests it the same way; only its
printf quoting differs. The `PHP_OS` hunk, `configure.ac` and
`main/php_config.h.in` only move. 0004, 0007 and 0009 get 8.5.13's line
numbers and add the same lines as before, and 0009 adds var_export's pad
(below). 0007 had to be refreshed: its first hunk applied only with fuzz 1,
because the function above it now returns `false`. Every patch now applies
to the 8.5.13 tarball with `patch -F0` and no offset.

What PHP 8.5.13 changes for this build:

- **var_export() gets a stack check (GH-24605).** It is the only new
  `zend_call_stack_overflowed` site in 8.5.13. 8.5.12-3's README lists it as
  unchecked, ending `php` with the RangeError past about 1500 levels. A check
  that sees only the shadow stack would not fire before the browser's
  stack runs out: on 8.5.12-3, `php_var_export_ex` takes 160 bytes of shadow
  stack per level, so 2048000 bytes last about 12800 levels. `patches/0009`
  gives it a 2032-byte pad (`ZEND_WASI_PAD_VAR_EXPORT`, the 42nd padded
  function), sized from that 1500 so the Error comes at about 62% of it. The
  limit was not measured again on 8.5.13.
- **GHSA-f6gg-rchx-xw8j (CVE-2026-128064).** The http wrapper's `use_ssl` was
  `ZSTR_VAL(resource->scheme)[4] == 's'`, so `HTTPS://` was plain http.
  0007 picks `https_proxy` from `use_ssl`, so on 8.5.12-3 a mixed-case
  HTTPS URL went to `http_proxy` as plain http on port 80, and its `ssl`
  context was never used. 8.5.13 compares the scheme case-insensitively, so
  the same URL is CONNECT plus TLS through `https_proxy`.
- **Session files:** `ps_files_write` now always calls `ftruncate(fd, 0)` and
  fails the write if that fails. `cert/server.mjs`'s PHPSESSID count (1, 2, 3
  through session files in /tmp) runs it on every request.
- **No change here:** the fiber changes (the callable's references, the
  catch-block fix) are in code that runs after `zend_fiber_init_context()`,
  which 0002 still fails with the FiberError. `zend_portability.h` (0003),
  `php_open_temporary_file.c` (0005) and `php_fopen_wrapper.c` (0006) are the
  same as in 8.5.12. The aligned-chunk mmap fix in `zend_alloc.c` is in the
  non-WASI branch that 0004 replaces. The VM's interrupt changes (a check
  at `FAST_RET`, no re-entry when the handler sets the flag again) don't
  change how 0008's SIGALRM sets the timeout. proc_open's change is
  Windows-only. The socket stream transport now rejects ports outside 0 to
  65535, and the sockets extension stays off. The OpenSSL changes are for
  OpenSSL 4.0, and this build links 3.5.9. The pdo_sqlite and phar fixes
  have nothing WASI-specific. The licence files are the same; uriparser
  1.0.3 keeps its COPYING.BSD-3-Clause.

The published 8.5.12-3 against this tree:

- build.sh's pad check, run on 8.5.12-3's `php.wasm` with this tree's
  patched 8.5.13 sources, fails on the new site alone:

  ```text
  homescoop wasix-php: patches/0009's stack pads are missing from php.wasm, so the stack check no longer counts the browser's stack (1 problems): php_var_export_ex takes 160 bytes of shadow stack, under php_var_export_ex's 2032-byte ZEND_WASI_PAD_VAR_EXPORT
  ```

- `cert/checklist.mjs` fails at its first assertion: its `php -v` is
  `PHP 8.5.12 (cli) (built: Oct 19 2026 17:02:46) (NTS)`, not 8.5.13's
  `(built: Nov 17 2026 14:30:51)`. `cert/licence.mjs` fails on SOURCES.md,
  which names `php-8.5.12.tar.xz`.
- `cert/stack.mjs`'s new `var_export` rows without an end (5000 levels of
  arrays and of objects) have no check to reach on 8.5.12, so 8.5.12-3 ends
  `php` with the RangeError (rc 70). That is the README's documented "past
  about 1500". 500 levels, the new depth rows, work on both.
- `cert/http.mjs`'s new row: on 8.5.12-3, `HtTpS://` with the decoy CA never
  starts TLS, so there is no `certificate verify failed`.

The spec rows above were not run against 8.5.12-3. Browser runs for this
change happen only on CI, and CI certifies only the head's tarball. The
8.5.12-3 results follow from 8.5.12's source and its README. The pad check
was run.

## 8.5.12-3: the published 8.5.12-2 fails the depth rows (#1705)

(Recorded for 8.5.12-3 on 2026-10-23.)

The published `@ai-ecoverse/wasix-php@8.5.12-2` against this tree's
`cert/stack.mjs` (slicc-kernel 1.146.5, users enforce) stops at its first
depth row:

```text
browser-cert: FAIL packages/wasix-php/cert/stack.mjs
AssertionError [ERR_ASSERTION]: serialize at depth 500: rc 0
Error: Maximum call stack size of 409600 bytes (zend.max_allowed_stack_size - zend.reserved_stack_size) reached. Infinite recursion?
```

Every depth row, run one by one on 8.5.12-2 (8.5.12-3 prints `ok` for each):

| row | 8.5.12-2 |
| --- | --- |
| `serialize` 500, arrays and objects | `Error: Maximum call stack size of 409600 bytes … reached. Infinite recursion?` |
| `==` on arrays 500, on `stdClass` objects 200 | `Error: Maximum call stack size reached during comparison` |
| `==` on objects with declared properties 500 | `Error: Maximum call stack size reached during object comparison` |
| `json_encode` 500, arrays and objects | false, `Maximum stack depth exceeded` |
| `array_map` 500, `array_walk_recursive` 500, `count(COUNT_RECURSIVE)` 500 | the 409600-byte Error |
| `var_dump` 200 | `nesting level too deep` in the output |
| `__toString` 200, `__get` 300, `preg_replace_callback` 200, `ArrayAccess` 300 | the 409600-byte Error |
| `http_build_query` 500 | `Error: Maximum call stack size reached.` |
| `usort` 150, `DOMDocument::saveXML` 500 | ok |

Compiling a 2000-deep constant array, a checked path, still ended `php` with
rc 70 on 8.5.12-2: its check is in `zend_check_stack_limit()`, which clang
didn't inline into `zend_eval_const_expr()`, so the 2 KiB frame was gone by
the time the recursion went on:

```text
RangeError: Maximum call stack size exceeded
    at php.zend_eval_const_expr (wasm://wasm/php-0887909e:wasm-function[10491]:0x7f7401)
    at php.zend_try_ct_eval_array (wasm://wasm/php-0887909e:wasm-function[10496]:0x7f97d6)
```

8.5.12-3 puts each pad in the frame of the function on the recursive path
(the README has the levels per path).

### The pad check in build.sh

build.sh reads the pads from the patched `Zend/zend_call_stack.h` and the
41 functions that take one from the patched sources, and fails unless each
function, or the one build.sh names it inlined into, subtracts at least its
pad from `__stack_pointer` in php.wasm. On this build it prints
`php.wasm: patches/0009's stack pads in 41 functions (24 sizes), each frame at least its pad: execute_ex 3600, php_var_serialize_intern 3200, zend_hash_compare 3280, php_array_user_compare_unstable 5792`.
Run on 8.5.12-2's php.wasm, it fails:

```text
homescoop wasix-php: patches/0009's stack pads are missing from php.wasm, so the stack check no longer counts the browser's stack (21 problems): execute_ex takes 2048 bytes of shadow stack, under execute_ex's 3600-byte ZEND_WASI_PAD_EXECUTE; php_array_user_compare_unstable takes 48 bytes of shadow stack, under php_array_user_compare_unstable's 5744-byte ZEND_WASI_PAD_USER_COMPARE; …; zend_eval_const_expr takes 32 bytes of shadow stack, under zend_eval_const_expr's 2048-byte ZEND_WASI_PAD_CONST_EXPR; zend_hash_compare takes 2048 bytes of shadow stack, under zend_hash_compare's 3280-byte ZEND_WASI_PAD_HASH_COMPARE; …
```

### Sizing the pads

Measured on builds of this tree with V8's baseline compiler only
(`--js-flags=--no-wasm-tier-up`, the shallowest the browser allows; with
tier-up the same paths go deeper). A first build sized every pad from
8.5.12-2's numbers and stopped `serialize()` at 462 levels:
`php_var_serialize_intern`'s 1080-byte buffer had shared the inlined 2 KiB
frame in 8.5.12-2 and now sits beside its pad, so the pad shrank by that
much. A second build put every measured path at 0.60 to 0.68 of its limit,
except compiling a constant array (0.81: its limit had moved from 1858 to
1499 levels between builds), whose pad grew from 1632 to 2048 bytes.
`ReflectionFunction::invoke()`, with no pad of its own, stops at 535 of 690
levels (0.78).

All of this is Chrome's V8 (the review browsers of homescoop's CI are Chromium as well, extension and cli kernel); Firefox and Safari are unmeasured.

prove-negative on the 8.5.12-3 build:
`prove-negative: emptied 1 module(s): bin/php.wasm`, then
`prove-negative: ok — cert failed on bad wasix-php tarball (status 1; 15 of 18 spec(s) failed: bailout.mjs, checklist.mjs, fd.mjs, fibers.mjs, heap.mjs, http.mjs, memory.mjs, openssl.mjs, process.mjs, server.mjs, sqlite.mjs, stack.mjs, tmp-phar.mjs, users.mjs, xml.mjs)`.

## 8.5.12-2: the published 8.5.12-1 fails the new specs

(Recorded for 8.5.12-2 on 2026-10-22; 8.5.12-3 replaced its single 2 KiB frame and 448 KiB budget.)

The published `@ai-ecoverse/wasix-php@8.5.12-1` against this tree's
`cert/` (slicc-kernel 1.145.0, users enforce):

- **openssl.cnf by default (#1690), `cert/openssl.mjs`:** with no
  settings, `openssl_pkey_new()` fails:

  ```text
  AssertionError [ERR_ASSERTION]: php rc=1
  stdout=nokey|error:8000002C:system library::No such file or directory|error:10000080:BIO routines::no such file|error:07000072:configuration file routines::no such file
  ```

  With the key rows skipped, `getenv("OPENSSL_CONF")` is empty
  (`'|missing|/etc/ssl/cert.pem'`).
- **the stack limit (#1689), `cert/stack.mjs`:** the issue's `php -r` of a
  5000-deep `serialize()` ends `php` with rc 70:

  ```text
  AssertionError [ERR_ASSERTION]: RangeError: Maximum call stack size exceeded
      at php.php_var_serialize_intern (wasm://wasm/php-0886f0aa:wasm-function[8587]:0x675ad9)
      at php.php_var_serialize_nested_data (wasm://wasm/php-0886f0aa:wasm-function[8595]:0x67ad1f)
  ```

  and `ini_get("zend.max_allowed_stack_size")` is false (the check isn't
  built). In 8.5.12-1, 500 levels of `serialize()`, `==` and `array_map()`
  recursion worked and 1000 ended in the same RangeError.
- `cert/licence.mjs` wants `patches/0009-zend-call-stack-wasi.patch`.

### Without parts of patches/0009

Measured on builds of this tree (the deepest level V8 allows is the same
in every build; the budget is the `-d zend.max_allowed_stack_size` at
which a recursion without end still throws PHP's Error and not a
RangeError):

- **Without the stack check** (8.5.12-1's configure, no
  `php_cv_have_stack_limit=yes`): no Error, every path below ends in the
  RangeError. V8 allows 331 levels of `usort()` calling itself, 652 of
  `__get()`, 628 of `__toString()`, 798 of `array_map()`, 939 of `==`,
  956 of `serialize()` and 1126 of `json_encode()`.
- **Without the 2 KiB frame** (`ZEND_WASI_CALL_STACK_FRAME`): the budget
  a path survives is 94 to 102 KiB for `==`, 125 to 133 for `usort()`, 196
  to 204 for `array_map()`, 227 to 235 for `__get()`, 852 to 860 for
  `__toString()` and 1180 to 1188 for `serialize()`. No size fits them
  all: 448 KiB leaves `==`, `usort()`, `array_map()` and `__get()` to the
  RangeError, and 80 KiB (under `==`'s) stops `__toString()` after 14
  levels and `serialize()` after about 16. A 1 KiB `volatile char` frame
  written at [0] did nothing (clang's SROA shrank it to one byte; 98 to
  113 KiB for `==`), so the frame is passed to an empty `asm` statement.
- **With it**, the budgets are 790 to 798 KiB for `usort()`, 1540 to 1548
  for `__get()`, 1860 to 1867 for `array_map()`, 1977 to 1985 for `==`,
  and over 2048 for `__toString()` and `array_walk_recursive()`, so 448
  KiB is about half of `usort()`'s and a quarter or less of the others'.
  The depths it allows: 94 levels of `==` on objects, 117 of
  `__toString()`, 124 of `json_encode()`, 167 of `__get()`, 174 of
  `usort()`, 177 of `array_map()`, 181 of `serialize()` and 188 of `==`
  on arrays.

- **The frame check in build.sh:** after `wasm-opt`, build.sh reads
  php.wasm's name section and fails unless `execute_ex`,
  `zend_hash_compare`, `zend_std_compare_objects` and
  `php_var_serialize_intern` each subtract at least 2048 from
  `__stack_pointer` (a later LLVM that dropped the frame would leave the
  check counting bytes again). On this build it prints
  `php.wasm: patches/0009's 2 KiB stack check frame in execute_ex 2048, zend_hash_compare 2048, zend_std_compare_objects 2064, php_var_serialize_intern 2128`.
  On 8.5.12-1's php.wasm, built without patches/0009, it fails:

  ```text
  homescoop wasix-php: execute_ex takes 0 bytes of shadow stack, not patches/0009's 2048-byte ZEND_WASI_CALL_STACK_FRAME, so the stack check no longer counts its levels
  ```

  (8.5.12-1's `zend_hash_compare` and `execute_ex` have no shadow frame,
  and `php_var_serialize_intern`'s is 1168 bytes.)

prove-negative on the 8.5.12-2 build:
`prove-negative: emptied 1 module(s): bin/php.wasm`, then
`prove-negative: ok — cert failed on bad wasix-php tarball (status 1; 15 of 18 spec(s) failed: bailout.mjs, checklist.mjs, fd.mjs, fibers.mjs, heap.mjs, http.mjs, memory.mjs, openssl.mjs, process.mjs, server.mjs, sqlite.mjs, stack.mjs, tmp-phar.mjs, users.mjs, xml.mjs)`.

## 8.5.12-1 (a new package)

A new package, so each patch's negative is the build or the cert case
without it, recorded while the recipe was written (PHP 8.5.12,
wasix-sysroot 2025.9.30-43, slicc-kernel 1.144.1 with users enforce).

### Without a patch

- **patches/0001 (configure for a wasi host):** PHP's own configure stops:

  ```text
  checking for ucontext.h... no
  configure: error: in `/tmp/php-wasix/neg/php-8.5.12':
  configure: error: fibers not available on this platform
  ```

  An earlier build without the PHP_OS hunk reported `PHP_OS` `Darwin`, the
  build machine's `uname` (`cert/checklist.mjs` wants `WASI`).
- **patches/0002 (fibers unavailable):** with configure's
  `ZEND_FIBER_UNAVAILABLE` but upstream's `zend_fibers.c`, the link fails:

  ```text
  wasm-ld: error: Zend/zend_fibers.o: undefined symbol: madvise
  wasm-ld: error: Zend/zend_fibers.o: undefined symbol: mprotect
  wasm-ld: error: Zend/zend_fibers.o: undefined symbol: make_fcontext
  wasm-ld: error: Zend/zend_fibers.o: undefined symbol: jump_fcontext
  ```
- **patches/0003 (setjmp):** `ext/iconv` doesn't compile (the asyncify
  sysroot's `<setjmp.h>` declares no `sigsetjmp`; every `zend_try` is
  `SETJMP`):

  ```text
  ext/iconv/iconv.c:468:2: error: call to undeclared library function 'sigsetjmp' with type 'int (__wasi_stack_snapshot_t *, int)'
  ```
- **patches/0004 (Zend MM chunks):** upstream's `zend_alloc.c` doesn't link
  (`wasm-ld: error: Zend/zend_alloc.o: undefined symbol: madvise`, its
  MADV_HUGEPAGE path), and its trim-to-alignment needs partial `munmap`s,
  which wasi-libc's emulation refuses with EINVAL. The first version of the
  patch took each chunk from `posix_memalign` and paid the alignment slack
  per chunk: `cert/heap.mjs`'s 400000-entry array, at
  `memory_get_usage(true)` 120 MiB, grew the wasm memory to 252 MiB
  (VmSize 258112 kB; 163 MiB with `USE_ZEND_ALLOC=0`). With the arena pool,
  162 MiB (165952 kB).
- **patches/0005 (P_tmpdir):** `sys_get_temp_dir()` returned `''` with no
  `TMPDIR`, `tempnam("", "x")` and `tmpfile()` returned false, and Phar
  failed:

  ```text
  Fatal error: Uncaught BadMethodCallException: Entry index.php does not exist and cannot be created: phar error: unable to create temporary file
  ```
- **patches/0006 (php://fd):** `ext/standard/php_fopen_wrapper.c:321:16:
  error: call to undeclared function 'getdtablesize'`.
- **patches/0007 (environment proxy):** every remote URL failed, http and
  https alike, while the kernel's `http_proxy`/`https_proxy` were set:

  ```text
  Warning: file_get_contents(http://example.test/hello): Failed to open stream: php_network_getaddresses: getaddrinfo for example.test failed: Name does not resolve
  ```
- **patches/0008 (max_execution_time):** `cert/bailout.mjs`'s
  `set_time_limit(1)` never fired: the 10-second busy loop printed
  `no timeout` and php exited 0 (`setitimer(ITIMER_PROF)` is EINVAL on
  WASIX).

### Cert cases that failed on the way (fixed in the specs, not the build)

- The http wrapper's `$http_response_header` is deprecated in 8.5 (the
  specs use `http_get_last_response_headers()`), and so are backticks.
- `openssl_pkey_new()` fails without an OpenSSL config file, which slicc
  doesn't have (`configuration file routines::no such file`); 8.5.12-1's
  checklist asserted that and passed one through `config` and
  `OPENSSL_CONF` (8.5.12-2 ships one, `cert/openssl.mjs`).
- A descriptor bash opens for a WASI program at fd 3 to 11 is shadowed by
  the kernel's preopened directories (`Is a directory`), so `cert/fd.mjs`
  checks fds 1, 2 and the error paths only.
